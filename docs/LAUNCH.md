## 1. DNS cutover (Cloudflare Pages)

The `_redirects` map (`dist/_redirects`, generated by `scripts/generate-static-files.mjs` from `build_map.py`'s `REDIRECTS`) assumes Cloudflare Pages.

1. **Done (2026-09-26).** Zone moved to Cloudflare (nameservers repointed from Namecheap to Cloudflare's `kallie`/`zac.ns.cloudflare.com`). `boxhauls.com` and `www.boxhauls.com` added as Workers Custom Domains on the `boxhauls` Worker via the API (`PUT /accounts/{account_id}/workers/domains`) — SSL certificates issued automatically for each.
2. **Done.** This required first deleting two pre-existing DNS records Cloudflare imported from the old Namecheap parking page (an apex `A` record and a `www` `CNAME`) — Custom Domains refuses to attach until any conflicting existing record is cleared. The zone's real records (`MX` for email, the Google Workspace `DKIM` `TXT`, and the `google-site-verification` `TXT`) were left untouched.
3. **Done.** `www` → apex handled via a Redirect Rule (Rulesets API, `http_request_dynamic_redirect` phase) rather than `_redirects` — confirmed Cloudflare Pages' `_redirects` format only accepts relative-path sources; a rule like `https://www.boxhauls.com/* -> https://boxhauls.com/:splat` fails deploy-time validation with `Invalid _redirects configuration: Only relative URLs are allowed` (hit and fixed during this project's first deploy attempt). The rule: hostname equals `www.boxhauls.com` → dynamic redirect to `concat("https://boxhauls.com", http.request.uri.path)`, 301, preserve query string.
4. **Done**, verified via real browser rather than `curl` — Cloudflare's Bot Fight Mode (on by default for new free zones) returns a `403`/JS-challenge to `curl` regardless of `User-Agent`, so `curl -I https://boxhauls.com/...` isn't a reliable check here. Confirmed instead that `boxhauls.com/`, `boxhauls.com/pricing/`, and `www.boxhauls.com/` (redirecting to apex, path preserved) all render the real site correctly in an actual browser.
5. See item 4 — same browser-based verification covers this.
6. **Done.** `truck-n-go.com` is hosted on Lovable; a domain-level redirect was configured there sending `truck-n-go.com/*` → `https://boxhauls.com/*` (path preserved) as a 301. Verified end-to-end: `truck-n-go.com/cost-to-move-a-couch` → `boxhauls.com/cost-to-move-a-couch` → `boxhauls.com/pricing/cost-to-move-a-couch/` (this repo's own `_redirects` catching the renamed path) lands on the correct final page. `www.truck-n-go.com` also redirects (via apex first). Keep this live for **at least 12 months** per map §12 — do not let the domain lapse or repoint it during that window.

## 3. Redirect test commands

Run every rule in `dist/_redirects` after cutover. Generated from the same source (`build_map.py`'s `REDIRECTS`) so this list can't drift from what's actually deployed:

```bash
for path in \
  /how-it-works /pricing /faq /contact /press /drive /partners \
  /link-to-us /blog \
  /services/on-demand-moving-and-hauling /services/furniture-delivery \
  /services/large-item-delivery /services/move-furniture \
  /services/single-item-movers /services/same-day-delivery \
  /services/local-hauling /services/truck-and-driver-for-hire \
  /services/small-moves /services/junk-hauling \
  /cities /cities/fresno \
  /cost-to-move-a-couch /cost-to-move-a-mattress \
  /cost-to-move-a-refrigerator /cost-to-move-a-washer-and-dryer; do
    echo "=== $path ==="
    curl -sI "https://boxhauls.com$path" | grep -iE "^(HTTP|location)"
done

# www -> apex
curl -sI "https://www.boxhauls.com/" | grep -iE "^(HTTP|location)"
```

Every line should show `HTTP/2 301` and a `location:` header pointing at the resolved target in `dist/_redirects`. Spot-check a couple of the `/blog/*` and `/cities/*` wildcard rules manually (e.g. `/blog/some-old-post-slug`, `/cities/austin`) since the loop above only covers exact-match rules.
